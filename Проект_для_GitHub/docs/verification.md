HTTP-проверки используют доверенный лабораторный CA; отключение TLS-верификации не применялось. Для разных пользователей cookie очищаются, поскольку Nextcloud может предпочесть ранее установленную сессию новым Basic-реквизитам. Отсутствие маркера само по себе не доказывает криптостойкость: оно подтверждает вместе с реализацией AES-GCM и сравнением хешей, что в проверенном облачном объекте хранится результат шифрования.

При первом запуске выявлено, что загрузка WebDAV через Guzzle использует системное хранилище CA контейнера. Добавлен воспроизводимый импорт публичного CA в nextcloud-entrypoint.sh; исходный код Nextcloud и проверка TLS не изменялись. Для доступа к Prometheus с localhost добавлена отдельная сеть monitoring-ui, поскольку контейнер только во внутренней сети не публиковал порт на этом стенде.

## Границы проверки

Не выполнены применение Kubernetes-манифестов, испытание NetworkPolicy на реальных узлах, публикация и облачные CI-запуски GitHub/GitLab. Разделение потребителя и провайдера на одном Docker-хосте функциональное; администратор этого ПК имеет доступ к обоим контурам. Сеть monitoring в Compose соединяет все микросервисы; направленное ограничение доступа к API обеспечивается проверкой реквизитов, а не только сетями Compose.

Подключение Nextcloud проверено через его настоящий серверный WebDAV API, включая внешнюю папку; ручной пользовательский сценарий в браузере и все функции Nextcloud этим не покрываются. Нагрузочные измерения, полное сравнение с контрольным вариантом и статистическая проверка гипотезы относятся к главе 4.
